CLI `0.162.0`，两组均使用现有配置中的 `gpt-6.1-sol`、推理强度 `medium`、服务层级配置 `default`；真实 turn context 确认模型与推理强度。每组使用独立临时 HOME、CODEX_HOME、Git 项目和记录库，项目安装同一候选源码的原生 Skill/桥接。其余全局规则、插件、hooks 未加载，凭据内容没有复制到证据；临时认证别名已清理。

验收源码是以 `eb36acaf933c5395c718b80a974021d5c2f53dfc` 为基线的 9 个候选文件。实际测试使用隔离源码 checkout，逐文件 SHA-256、完整补丁哈希见 [summary.json](summary.json) 和 [candidate.patch](candidate.patch)。真实运行后确认候选文件没有改变，待提交工作区的这 9 个文件与已测试内容一致。候选尚未提交时先验收，因此不编造候选 commit ID。

两组各六回合，共 **12 个模型回合、10 个不同会话**。每个回合上限 240 秒，全部 CLI 退出码为 0，无超时、重试或提示调优：

1. 自然任务修复订单编号，先复现 int 转换破坏原文，再验证修复。
2. 用原 thread ID 恢复同一会话，补充空字符串拒绝、首尾空格保留的合同。
3. 新会话续接，询问最新状态和验收缺口，不改业务代码。
4. 新会话修复客户编号入口，合同与订单相同。
5. 新会话修复供应商编号入口，参考以前处理。
6. 新会话提出展示用语偏好，不改业务代码。

前三个业务模块在各自任务开始前才加入。前四个提示与[修复前对照](../2026-10-30-ab/report.md)相同，全部业务提示均未要求保存、创建经验、采用指定编号或运行指定脚本。没有显式经验整理兜底。项目约定只声明记录库已授权。完整提示、线程、耗时、命令与产物见归档。
