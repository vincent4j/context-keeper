# 保存本次上下文

## 步骤

1. **分析信息来源**
   - 回顾当前对话，提取用户需求、技术决策、解决的问题。
   - 优先运行 `scripts/context_keeper_probe.py status --root <repo>` 获取限量 git 状态。
   - probe 已包含 `git status --short --branch`、`git diff --name-status HEAD`、`git diff --stat HEAD` 时直接复用，不重复运行；只有输出缺项时才单独补查。
   - 只有需要理解语义时，才运行 `git diff HEAD -- <file...>`；不要默认输出全量 `git diff HEAD`。
   - 判断任务复杂度：简单任务用 1-2 段复盘；复杂任务可写结构化复盘。

2. **推断功能模块名称**
   - 从对话内容中自动推断，例如 "Solutions页面导航栏添加"。
   - 用于文件命名，应简洁准确；不确定时询问用户。

3. **生成文件名**
   - 格式：`YYYY-MM-DD-[功能模块]`。
   - 同一对话多次保存时覆盖同一文件；不同对话同天同模块冲突时加 `-2`、`-3`。

4. **按需生成需求文档** → `docs/plans/YYYY-MM-DD-[功能模块]需求.md`
   - `feature` / `research` 或有明确产品需求时生成。
   - `refactor` / `bugfix` / `config` / 纯维护或文档整理时跳过。
   - 模板章节：需求概述、功能结构、数据来源、技术要求、设计要求、验证标准、参考资料。

5. **生成工作日志** → `docs/worklog/YYYY-MM-DD-[功能模块].md`
   - 包含：任务概述、完成的工作、问题和解决方案、本次对话复盘、复盘分级、给用户看的增量认知、文件清单、技术决策、下一步。
   - 复盘分级分为：普通复盘、重要经验、合同候选。
   - “给用户看的增量认知”只保留 0-3 条用户可能尚未意识到、且会影响判断或后续行动的信息。可用类型：盲点、复盘、隐患、决策影响、合同候选。
   - 禁止写入：完成项、测试通过、修改文件、commit、push，以及对话中已经明确告诉用户的普通事实。
   - 每条必须是总结后的“一句认知 + 一句影响”，认知不超过 120 字，影响不超过 80 字：

   ```markdown
   ## 给用户看的增量认知

   - **盲点：** [用户可能尚未意识到的事实或边界]
     - **影响：** [它会怎样影响判断或下一步]
   - **隐患：** [尚未成为故障但值得提前注意的风险]
     - **影响：** [不处理可能带来的后果]
   ```

   - 没有新增认知时，章节下只写：`本轮未发现需要额外提醒的盲点或隐患。`，不要凑内容。
   - 快速摘要必须位于末尾，控制在 100-150 个上下文 token：

   ```markdown
   ## 快速摘要（用于下次对话）

   **类型：** [feature|bugfix|refactor|research|config] | 项目：[项目名]
   **完成：** [一句话描述完成的工作]
   **问题：** [遇到了什么问题 + 怎么解决的；没有则省略]
   **经验：** [学到了什么 + 下次怎么做；没有则省略]
   **下一步：** [下一步计划]
   **文件：** [关键文件列表]
   ```

6. **更新项目记忆** → `docs/memory-keeper.md`
   - `memory-keeper.md` 是历史经验和合同候选索引，不是硬约束来源。
   - 不存在时创建文件头：

   ```markdown
   # 项目记忆索引

   ## 主题摘要（按类型）

   ---

   ## 时间线（最新在前）

   ---
   ```

   - 新条目追加到时间线顶部：

   ```markdown
   ## YYYY-MM-DD - [功能模块] `[类型]`
   - **模块：** [模块名或功能域]
   - **触发词：** [需求、报错、字段、接口、文件名、模型名等]
   - **任务：** [一句话描述任务]
   - **关键经验：** [最重要的 1-2 条经验，合并为一行]
   - **合同候选：** [强约束；没有则写“无”]
   - **详见：** [worklog/YYYY-MM-DD-[功能模块].md](worklog/YYYY-MM-DD-[功能模块].md)
   ```

   - 主题摘要区块每类只保留最近 3 条关键词；整个区块控制在 150 个上下文 token 以内。

7. **按需更新相关文档**
   - 只更新真正需要的 README、architecture、design system 或其他项目文档。
   - 不为保存上下文顺手改无关文档。

8. **输出用户可能没意识到的内容**
   - 输出工作日志“给用户看的增量认知”，目的不是汇报完成情况，而是补充盲点、复盘、隐患和决策影响。
   - 最多 3 条，每条只有一句认知和一句影响；没有则只输出无新增提醒，不凑数。
   - 写完 worklog 和 memory 后必须运行：

   ```bash
   python3 <skill-dir>/scripts/context_keeper_probe.py save-report --root <repo> --worklog <worklog>
   ```

   - 命令会验证快速摘要、增量认知的类型与长度、项目记忆反向链接，并生成精简用户报告。非 0 时必须先修正文档。
   - 保留命令生成的内容供用户交付，不要替换成普通任务摘要，也不要额外补写用户已经知道的完成项。

   ```text
   已保存上下文。

   你可能还没意识到：
   1. [盲点/复盘/隐患/决策影响/合同候选] ...
      影响：...

   详细内容：
   - 工作日志：[docs/worklog/...](...)
   - 项目记忆：[docs/memory-keeper.md](...)
   ```

9. **询问是否提交代码**
   - 用户尚未授权提交时，文档保存完成后输出增量认知，并询问是否提交、推送。
   - 用户选择提交时，先看 `git status --short`；如果存在明显无关改动，只 stage 本轮相关文件，不默认 `git add -A` 打包无关改动。
   - 用户一开始已明确要求提交或推送时，不再重复询问，也不在 commentary 重复第 8 步内容；校验通过后直接执行 Git，并在最终回复交付一次。
   - “本轮相关文件”以当前对话明确产生或确认的改动为准；无法区分既有脏改动时停止并询问，不把整个工作区默认打包。

10. **最终回复门禁**
    - 如果保存、提交或推送发生在同一回合，最终回复必须同时包含：第 8 步增量认知、工作日志与项目记忆链接，以及必要的 commit、分支、推送和工作区状态。
    - Git 结果只用最短必要信息表达，不得把完成清单重新扩写成摘要。
    - 最终回复必须自包含；同一回合已经在 commentary 展示过用户报告时，最终回复仍需保留增量认知，但不要再扩写或复述普通进度。
    - 任一项缺失时不得说“已完成 Context Keeper”或结束回合。
