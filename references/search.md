# 查找历史经验

## 写入经验前的候选查找

准备写入经验时使用 `search --for-write --query '<主题和对象>'`。该模式只查询当前项目的经验，不扩展到普通日志或用户级经验。输出是合并候选，包含已替代历史的定位，按提示打开替代链接核对当前条目。候选上限和截断会如实报告。查找只读，新旧结论是否相容、证据是否支持修订，按保存说明判断。

## 何时检索

用户不需要提供 Skill 名称或关键词。出现以下信号时，从当前上下文自动提取模块、业务词、错误码、字段、接口、文件、模型或测试名：

- 用户明确说以前、上次、又出现、按之前的方法。
- 当前失败，准备重复尝试或换路线，且本轮证据不足。
- 准备推翻旧决策，但原始依据不在当前上下文。

普通新需求不检索。同一问题本轮只查一次，除非出现新证据。

## 根据问题使用记录

- 查询“当时发生过什么”：以日志中的实际操作、观察和当时判断为依据；经验和索引用于定位。错误方案和失败尝试同样是历史事实。
- 查询“现在应该怎么做”：优先当前有效经验及适用范围，再核对来源日志和当前条件。旧日志中的当时判断不能直接当作当前建议。
- 续接进度：按 [续接说明](resume.md) 优先当前主题和待办，再用历史线索追溯；旧日志首次摘要不代表当前进度。

工作日志只追加。检索发现错误不回改原日志，需记录时在当前会话追加说明；主题记忆可更新当前认识并保留来源与替代关系。

## 分层搜索

先运行限量搜索：

```bash
python3 <skill-dir>/scripts/context_keeper_probe.py search \
  --root <repo> --query '<关键词1|关键词2|关键词3>'
```

普通空白分隔的多关键词按任一词命中召回；显式正则中的分组、转义、量词和 `|` 保留原语义，不把表达式内部空格拆词。候选数量与读取预算不变。该规则仅适用于 search/resume，history-search 的原正则行为不变。

脚本依次查：

1. 项目和已批准用户级的 evolution 主题经验；默认排除已替代经验，最多返回 3 条。
2. `memory-keeper.md` 当前主题摘要、项目要求/约定小节（保留同条目的来源和下一步），结果明确标为当前记忆。
3. 时间线及有限回退的 plans、工作日志，明确标为历史。

当前时间线检索不直接覆盖 compact 归档区；有限回退也不能保证完整召回。第一阶段不改检索算法，不把归档记录仍存在等同于 search 已完整覆盖。

首轮最多返回 5 个候选。深读只展开最相关的 1～2 份事实来源文件，用于定位的索引不挤占这两份依据；引用索引摘要中的结论仍需核对来源。单次展示通常不超过 80 行，不是整个会话累计 80 行硬限。自动搜索零命中就停止；不要为了碰运气扩大到整个仓库或所有对话。

普通search展示经验正文、索引回退或工作日志/计划命中片段时，如文件内还有匹配行未展示，会在对应候选下输出“文件内匹配展示受限”。提示不占候选位，不扩大默认命中行数，也不证明存在反证；仅表示片段不能作为完整结论。该提示不覆盖当前主题、时间线摘要及单行字符裁剪，也不应用于输出字段摘要的 `--for-write`。

### 在已定位来源中定点读取

片段有匹配截断、日志有后续追加或结论冲突时，先在已选的 1～2 份文件内按当前问题的关键词找行号，再读相邻上下文；固定 `head`/`tail` 只能展示窗口，不能证明中段没有纠正。不要先过滤掉未核清的行再取尾部。没有上述信号且当前依据足够时，不额外检索。

例如已从候选定位一份日志后，在实际路径和关键词确认后执行：

```bash
rg -n -F -m 12 -- '当前问题关键词' 'docs/context-keeper/worklogs/已定位的日志.md'
sed -n '40,65p' 'docs/context-keeper/worklogs/已定位的日志.md'
```

第二步行区间按实际命中位置选择，示例数字不是固定读取窗口。`-F` 按字面匹配，`--` 防止关键词被解释成选项。若达到 12 个匹配，按展示受限处理，不能据此前缀宣称没有后续纠正；在同一已选来源内收窄到更具体的问题字段，或按已发现的追加位置定点核对，仍控制单次展示，不升级为全库扫描。多次定位同文件不增加事实来源份数；命令帮助、参数准备等成本另外报告，不能把实验自设的命令次数上限冒充产品合同。

截断与零命中必须区分：达到 `--scan-worklogs` 扫描上限且仍有未扫描候选时，命令输出“检索不完整”并给出未扫描数量；达到候选输出上限且仍有来源未检查时，输出“候选/覆盖受限”说明。实际扫完所有候选的零命中不附带上述提示，不能当作截断结果；出现提示也不要为补全而追加全量扫描，如实转述覆盖边界即可。

只有用户明确要求原文，或关键判断无法由项目记录支撑时，才运行：

```bash
python3 <skill-dir>/scripts/context_keeper_probe.py history-search \
  --root <repo> --query '<关键词>'
```

该命令按项目筛选 Codex 和 Claude Code 的原始会话，只输出有限命中片段和定位。Codex 优先使用本机状态库中与当前 `cwd` 对应的 rollout 路径；有更新时间字段时按更新时间倒序，否则按状态库行号倒序。消息库未命中时，先读这些已知路径（包括不在 `sessions` 目录的归档文件）；尚有候选额度时再有限回退 JSONL 目录，以覆盖部分或空索引。无索引回退按目录遍历顺序取候选，不能保证最近历史优先。Claude Code 仍逐条核对记录中的 `cwd`，不会只因目录名相近而纳入结果。

默认在 Codex 与 Claude Code 合计最多选取 500 个候选文件、读取 8 MiB 原始消息，并使用 3 秒协作式时限；可按需收紧：

```bash
python3 <skill-dir>/scripts/context_keeper_probe.py history-search \
  --root <repo> --query '<关键词>' --scan-files 50 --max-bytes 1048576 --timeout-seconds 1
```

候选发现只读取有限文件元数据，不会先对整个历史目录全文搜索。`--scan-files` 在内容读取前生效；已索引路径即使由 SQLite 消息库命中，也占用全局候选文件额度。部分索引、目录遍历顺序和候选截断都可能遗漏更早或未索引的记录，不能把未命中当作全召回。`--max-bytes` 只限制返回到 Python 的 JSONL/SQLite 原始消息字节总量，截断行也会计入；state 中的线程 ID 和路径属于候选元数据，只受候选数量限制，不占消息预算。JSONL 使用固定块的无缓冲读取，避免在逻辑上限外预读并在每块之间检查时限；SQLite 每条消息按当时剩余额度单独提取。SQLite 的 `LIKE` 仍可能在 SQLite 引擎内部扫描数据库页，这部分不是可按记录字节计量的返回数据，但查询配置了同一协作式时限和收敛的 busy timeout。本地单条 SQLite 操作和文件系统调用无法被 Python 强制中断；因此超时是检查点式边界，不是杀进程式硬超时。参数必须为有限正数。

任何限制触发时，命令会明确输出“检索不完整：预算耗尽（…）”。此时无论是否有命中，都不能把结果当作完整检索或完整零命中；找不到时如实说明，不扩大成全盘扫描。

## 输出规则

输出应回答：找到了哪次记录、当时有什么事实、本次是否适用及原因。必须遵守：

- 原始记录、项目摘要、Agent 推断分开标识。
- 用户记忆与记录不一致时展示事实证据，不迎合、不猜测。
- 记录冲突时展示差异、日期和适用范围。
- 未命中只说当前检索未找到证据，不得断言历史上从未发生。
- 经验命中只用于提醒和选择动作；版本、输入或目标变化时必须重新判断适用性。
- 待验证经验（含缺状态字段的默认值）在结果中标注“待验证，仅供核查，不作为执行建议”；其命中片段统一加“（待验证，暂停采用，仅供核查）”前缀，包括多行建议动作的续行，不得当作有效推荐转述；已验证经验可引用其建议动作，仍需核对适用范围；已替代经验不得作为当前建议。

实际采用某条经验并影响了判断或动作后，在对话中简短告诉用户；只有得到本轮结果证据后，才能说复用有效。经验闭环的判定与修订规则见 [保存说明](save.md) 第 5 节。
